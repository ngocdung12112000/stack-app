StackShop Architecture Cheat Sheet

.NET 8 microservices behind a YARP gateway, a Next.js BFF in front, one database per service, and three brokers that each do one job.

One broker, one job 04-messaging §1

Kafka
Domain events (past tense)
  • One topic per aggregate, key = aggregateId, so events stay in order per order/product
  • Many consumer groups, replayable
  • Type: ordering.order-paid.v1
  • Retry topics, then <topic>.dlq
RabbitMQ
Commands and work jobs
  • SendEmail, PushInApp, ProcessImage
  • Competing workers of one consumer
  • Delayed retry 10s, 1m, 10m, then DLX
  • MassTransit v8 only
SQS (LocalStack)
Inbound webhooks, long jobs
  • payment-webhooks.fifo (group = provider payment id)
  • shipping-webhooks, report-export-jobs
  • Long poll 20s, delete only after success, redrive DLQ

The frontend never touches a broker. Delivery is at-least-once with idempotent consumers, which makes it effectively once.

Publishing an event: outbox 04-messaging §6

  1. Handler changes the aggregate, which collects domain events.
  2. An EF SaveChangesInterceptor writes them to outbox_messages in the same transaction (a Mongo transaction for catalog and review).
  3. OutboxRelay polls every 500ms with FOR UPDATE SKIP LOCKED, produces to Kafka, waits for the ack, sets processed_at.
  4. Consumer handles the message and stores (msgId, consumer) in its inbox in the same transaction, then commits the offset.
  5. Transient error: retry 3x in process, then retry topic. Poison message: straight to DLQ.

Checkout saga 04-messaging §7

Pendingstock-reserved → AwaitingPaymentpayment.succeeded → Paidshipment-created → Processingin transit → Shippeddelivered → Delivered
  • reservation-failed in Pending → Cancelled (out of stock)
  • payment.failed or 15 min deadline → Cancelled; inventory and coupon usage released
  • Admin cancel after Paid → Cancelled → Refunded

Orchestrated by ordering, state in saga_state, SagaTimeoutWorker every 30s. Inventory reserves all-or-nothing (TTL 15m) and expires reservations on its own. POST /orders returns 202 with the order id. Only the webhook, never the browser redirect, decides the payment outcome.

Rules that are easy to break

  1. A service never references another service's code.
  2. Never read another service's database. Use events, gRPC or REST via the gateway.
  3. Publish only through the outbox, in the same transaction as the state change.
  4. Consumers dedupe by message id (inbox).
  5. Order status changes only through the Order aggregate state machine.
  6. Re-validate prices and stock synchronously at checkout. Cache, cart and search copies are for display.
  7. Webhooks: verify HMAC, enqueue to SQS, return 200. Nothing else.
  8. MassTransit v8 only. v9+ is commercial.
  9. Never use IDs as metric labels.
  10. No PII in logs.

Three repos ADR-001

stackshop-backend · services, gateway, mock-psp, building-blocks, contracts (events, protos, openapi), api-client, Seeder, k6
stackshop-frontend · pnpm + Turborepo: apps/web, apps/admin, packages/ui (shadcn), Playwright e2e
stackshop-infra · local compose, K8s Kustomize, ArgoCD, dashboards and alerts
Cross-repo merge order:backend→client publish→frontend→infra

App repos build images and open tag-bump PRs in infra. Only ArgoCD deploys. Public API changes stay backward compatible for one frontend release.
